# Agent 的 Memory 到底是不是“记忆”？

人类说“我记得”时，通常意味着过去经历在脑中留下了可被唤起的痕迹。Agent 的 Memory 很容易借用这种直觉，但工程实现更朴素：

```text
写入外部存储 → 在未来检索 → 选择一部分 → 放回模型 Context
```

模型并没有在两次 API 调用之间持续保持意识。某段信息如果没有被重新放进当前输入，对这一轮模型来说就等于不存在。

## 先拆开最容易混淆的几层

### Conversation History：发生过什么

最直接的做法，是保存消息列表：

```json
[
  {"role": "user", "content": "我下周去上海"},
  {"role": "assistant", "content": "好的，需要规划行程吗？"},
  {"role": "user", "content": "帮我订周二晚上的酒店"}
]
```

第二轮中的“上海”来自历史消息。Conversation History 是原始事件记录，优点是保真，缺点是会无限增长。

它并不自动等于 Memory。只有当 Runtime 保存并在后续选择性注入时，它才发挥记忆作用。

### Context：这一轮能看到什么

Context 是一次模型调用的即时工作区。它可能包含最近对话，也可能包含工具结果、系统规则、检索知识和任务状态。

Context 具有三个性质：

- 有长度上限；
- 调用结束后不会自动持续；
- 内容由 Runtime 在每一轮重新构造。

因此把完整历史放进 Context，只是一种最简单的 Memory 读取策略，不是 Memory 的定义。

### Short-term Memory：当前任务还需要什么

短期 Memory 保存当前任务中的临时事实，例如：

```json
{
  "destination": "上海",
  "check_in": "2026-10-06",
  "budget_cny": 800,
  "candidate_hotels": ["hotel_17", "hotel_42"],
  "pending_question": "是否需要早餐"
}
```

它通常按 Session 或 Run 隔离，任务结束后可以删除或归档。相比反复扫描聊天记录，结构化字段更稳定，也更容易校验。

### Long-term Memory：跨任务保留什么

长期 Memory 保存未来仍可能有用的信息，例如用户偏好、项目决策或已验证经验：

```json
{
  "subject": "user_123",
  "fact": "酒店预算通常不超过 800 元",
  "source": "session_20260930",
  "confidence": 0.92,
  "valid_from": "2026-09-30",
  "expires_at": null
}
```

“长期”描述生命周期，不代表信息永远正确。偏好会变化，项目决策会废弃，Memory 需要版本、来源、置信度和失效机制。

## Vector DB 不是 Memory 的同义词

向量数据库解决的是相似性检索：

```text
文本 → Embedding → 向量
查询 → Embedding → 找相近向量
```

它适合召回语义近似的非结构化片段，比如过去讨论过的设计决策。但它不擅长所有问题：

- “用户最新预算是多少”需要按时间和字段精确查询；
- “订单是否已经支付”需要权威业务数据库；
- “任务当前执行到第几步”需要 State Store；
- “过去哪条经验与这个错误相似”才适合向量检索。

把所有东西都塞进 Vector DB，会丢失精确更新、唯一约束、排序和事务语义。

## KV Store 解决另一类问题

键值或关系存储更适合确定性事实：

```text
user:123:preferred_language → zh-CN
run:456:current_step        → 7
project:abc:deploy_region   → cn-north
```

它可以精确覆盖旧值，读取成本稳定，也容易做权限隔离。代价是写入前必须知道结构，不能像向量检索那样用自然语言模糊召回。

成熟系统常组合使用：

```text
KV / SQL       → 身份、偏好、状态、约束
Vector Store   → 非结构化经历与语义片段
Object Storage → 大文件、完整轨迹、原始证据
```

Memory 是这一整套写入和读取策略，不是哪一种数据库产品。

## Summary Memory 会压缩，也会失真

当历史超过 Context Window，可以把早期对话总结成：

```text
用户计划 10 月 6 日入住上海酒店，预算 800 元，
偏好靠近地铁，尚未确认是否需要早餐。
```

Summary 降低 Token 消耗，却引入信息损失。原始对话可能还说过“预算必要时可到 1000 元”，摘要若省略这句话，后续推荐就会偏窄。

因此 Summary 最好满足：

- 保留指向原始消息的引用；
- 区分用户原话与模型推断；
- 对关键数字、日期、否定词做结构化提取；
- 允许新事实覆盖旧事实；
- 重要操作前回看权威原文。

Summary 是有损索引，不应成为唯一事实来源。

## Memory 的完整生命周期

### 1. Capture：哪些内容值得候选

不能把每句话都永久保存。闲聊、临时验证码、错误推测和敏感信息不应默认进入长期 Memory。

候选规则可以结合：

- 用户显式要求“记住”；
- 信息是否会跨任务复用；
- 是否来自可信来源；
- 是否涉及敏感数据；
- 是否已有同类事实。

### 2. Consolidate：如何整理与去重

新消息说“预算改成 1000”，系统不应同时把 800 和 1000 当作当前值。需要合并、覆盖或建立时间版本。

```json
{
  "key": "hotel_budget",
  "value": 1000,
  "supersedes": "memory_older",
  "observed_at": "2026-10-01"
}
```

### 3. Retrieve：当前问题需要找什么

检索不是只看向量相似度。常见评分还包括：

```text
score =
  semantic_similarity
  × recency_weight
  × source_trust
  × task_relevance
  × permission_filter
```

权限过滤必须在召回前或召回时完成，不能先把其他用户的内容取出，再指望 Prompt 要求模型忽略。

### 4. Select：多少信息进入 Context

召回 100 条不等于全部注入。Context Builder 要去重、排序、控制 Token，并标注来源。低置信度内容可以告诉模型“这是待核验线索”，不能伪装成事实。

### 5. Forget：什么时候删除或失效

遗忘是 Memory 系统的一等能力：

- 用户要求删除；
- 数据超过保存期限；
- 新事实替代旧事实；
- 来源被证明错误；
- 项目或 Session 已关闭；
- 权限关系发生变化。

只会写不会忘的 Memory，最终会成为过时信息和隐私风险的集合。

## 一个典型错误：模型把推测写成事实

用户说：

> 我最近在看 Go，也许以后会用。

模型总结成：

```text
用户的主要编程语言是 Go。
```

下次检索时，这条推断以确定事实的形式进入 Context，Agent 开始默认生成 Go 代码。多轮以后，错误会被自身输出反复强化。

解决方法不是让模型“更谨慎”一句话，而是改变数据结构：

```json
{
  "content": "用户最近在了解 Go",
  "kind": "interest",
  "source_quote": "我最近在看 Go，也许以后会用",
  "inference": false,
  "confidence": 1.0
}
```

若需要推断，应单独标记：

```json
{
  "content": "用户未来可能采用 Go",
  "kind": "hypothesis",
  "inference": true,
  "confidence": 0.45
}
```

事实与推断不分，是长期 Memory 最危险的污染来源之一。

## Memory 如何被评测

不能只问“它记住了吗”，至少要分别评估：

| 阶段 | 指标 |
| --- | --- |
| 写入 | 该存的是否保存，不该存的是否拒绝 |
| 更新 | 新事实能否正确覆盖或并存 |
| 召回 | 相关事实是否进入候选，Recall@K |
| 精排 | 过期、低可信内容是否被降权 |
| 使用 | 模型是否正确引用，而非曲解 |
| 遗忘 | 删除后是否从索引、缓存和备份路径失效 |

最终回答正确，并不能证明 Memory 正确。模型可能凭参数知识猜对；同样，召回正确也不保证回答正确，模型可能忽略了它。

## 所谓“记忆”，是系统能力而非模型器官

从用户体验看，Agent 确实表现得像“记得我”。从工程机制看，这种连续性来自一条外部管道：

```text
过去事件
→ 选择与结构化
→ 持久化
→ 检索与权限过滤
→ Context 注入
→ 当前模型决策
```

因此问题“Agent 的 Memory 到底是不是记忆”有两个答案：

- 在交互层，它可以提供类似记忆的连续体验；
- 在实现层，它是外部存储、检索、压缩和上下文编排机制。

理解第二个答案很重要。只有把 Memory 当成数据系统，才能讨论一致性、来源、过期、隐私、删除和评测；否则“记忆”只会成为一个拟人化词语，掩盖真正需要设计的工程细节。
