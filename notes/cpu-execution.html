02.02 / CPU / ZH

CPU 到底在执行什么？

从表达式进入汇编和机器码，解释寄存器、ALU、Pipeline 与 Cache 如何协作。

从源代码看：

long add(long a, long b) {
    return a + b;
}

人看到的是变量、加法和返回值。CPU 看不到 long、函数名或 C 语义。它看到的是一段内存中的字节，以及一组正在变化的架构状态：

指令指针 + 寄存器 + 标志位 + 内存

CPU 的工作，是按照指令集架构解释机器码，让这些状态一步步发生变化。

从源代码到汇编

在 x86-64 System V ABI 下，编译器可能把上面的函数编译成：

add:
    lea rax, [rdi + rsi]
    ret

这里：

  • 参数 a 位于寄存器 RDI；
  • 参数 b 位于 RSI；
  • 返回值放进 RAX；
  • LEA 计算地址表达式，但编译器也常用它做整数加法；
  • RET 从栈中取回返回地址，继续执行调用者。

也可能生成：

mov rax, rdi
add rax, rsi
ret

两者在此语义等价。具体结果取决于架构、优化级别与编译器版本。

汇编仍然是给人看的助记符。CPU 接收的是编码后的字节。例如某种 x86-64 编码可能形如：

48 8d 04 37 c3

字节本身没有“加法”标签。取指与解码电路按照 x86-64 ISA 规则，把它们解释成操作及操作数。

ISA 是软件与 CPU 的合同

Instruction Set Architecture，指令集架构，规定：

  • 有哪些指令；
  • 寄存器对软件呈现什么名字和宽度；
  • 指令如何编码；
  • 内存寻址方式；
  • 异常与中断语义；
  • 特权级；
  • 原子操作和内存模型。

编译器面向 ISA 生成机器码，CPU 厂商实现 ISA。

同样执行 x86-64 的 Intel 与 AMD 处理器，内部流水线、Cache 大小和执行单元可以完全不同，只要最终可观察结果符合 ISA。

这一区分很重要：

ISA             = CPU 对软件承诺“看起来怎样”
Microarchitecture = 芯片内部“具体怎样做到”

CPU 眼中的程序是什么

在最小模型里，程序可以表示为：

Stateₜ = {
  RIP: 下一条指令地址,
  Registers: 通用寄存器与状态寄存器,
  Memory: 当前地址空间可访问的字节,
  Flags: 上次运算产生的条件状态
}

Instruction(Stateₜ) → Stateₜ₊₁

例如：

add rax, rsi

在架构层面意味着：

RAX ← RAX + RSI
RFLAGS ← 根据结果更新部分标志
RIP ← 下一条指令

函数、对象、切片、闭包都必须先被编译成这种状态变化。CPU 不知道一块内存是“用户对象”还是“缓存”，除非指令和软件约定赋予它含义。

Register：CPU 最近的工作位置

寄存器位于处理器核心内部，是指令最直接操作的状态。

常见类别包括：

  • 通用寄存器：整数、地址、参数与临时值；
  • 指令指针：下一条指令的位置；
  • 栈指针：当前线程栈顶；
  • 标志寄存器：零、进位、溢出等条件；
  • 向量寄存器：SIMD 数据；
  • 控制寄存器：页表、特权和处理器配置。

源代码变量不必一一对应寄存器。优化器可能：

  • 完全消除变量；
  • 将常量直接折叠；
  • 让多个变量复用一个寄存器；
  • 把寄存器不足的值 Spill 到栈；
  • 把循环中的多个元素放入向量寄存器。

因此调试优化程序时，源码变量可能显示为“optimized out”，因为机器层已经没有那个独立实体。

ALU：真正做加法的地方

Arithmetic Logic Unit 执行整数加减、位运算、比较等操作。现代核心不只有一个 ALU，通常还有：

  • Load / Store Unit；
  • 浮点和向量执行单元；
  • 分支单元；
  • 地址生成单元；
  • 乘除法单元。

一条 ADD 不是“整个 CPU 做一次加法”，而是被调度到能执行该操作的某个端口和单元。多个互不依赖的微操作可以在同一周期并行执行。

为什么需要 Pipeline

如果 CPU 必须完整执行完一条指令，才开始读取下一条，很多硬件会空闲。

经典教学流水线分为：

Fetch → Decode → Execute → Memory → Write Back

当第 1 条指令进入 Execute，第 2 条可以 Decode，第 3 条可以 Fetch。它像工厂流水线，提高单位时间完成的指令数。

现代高性能 CPU 更复杂，通常还包括：

取指
→ 分支预测
→ 解码
→ 重命名
→ 分派
→ 乱序执行
→ 写回
→ 按程序顺序退休

“退休”表示一条指令的结果成为架构上正式可见的状态。内部可以乱序执行，但对单线程程序必须表现得像遵循 ISA 规则。

一条指令可能被拆成多个微操作

x86 指令长度可变、语义复杂。前端解码器可能把一条机器指令拆成更简单的 Micro-ops。

例如“从内存取值再加到寄存器”在内部可能包含：

地址计算
→ Load
→ Integer Add

CPU 后端根据数据依赖和执行单元空闲情况调度这些微操作。ARM 等 RISC ISA 的编码通常更规则，但现代实现同样会做复杂的内部调度。

机器码是架构接口，Micro-op 是具体微架构的内部语言，二者不能混为一谈。

乱序执行：代码顺序不等于物理执行顺序

考虑：

mov rax, [address_a]   ; 可能等待内存
add rbx, rcx          ; 与上一条无依赖
imul rdx, r8          ; 也无依赖

如果第一条发生 Cache Miss，按序等待会浪费大量周期。乱序执行核心可以先完成后两条，再等待 Load。

它需要：

  • 寄存器重命名，消除虚假的名字依赖；
  • Reservation Station 或调度队列；
  • Reorder Buffer 追踪程序顺序；
  • 精确异常机制，保证出错时状态一致。

最终提交仍按程序顺序进行，所以软件通常感知不到内部乱序。

分支预测：先猜下一条在哪里

遇到：

if (x > 0) {
    y++;
} else {
    y--;
}

CPU 在比较结果出来前就需要继续取指，否则 Pipeline 会停顿。分支预测器根据历史猜测走哪条路径，并投机执行。

猜对时节省等待；猜错时，错误路径上的未退休结果被丢弃，Pipeline 重新填充，付出若干到数十周期代价。

这解释了为什么相同指令数量的代码，运行时间可能不同。程序性能不仅取决于“执行了多少条”，还取决于依赖、Cache 命中和预测准确率。

Cache：CPU 为什么不能直接等内存

执行单元一个周期可能完成多次运算，但访问 DRAM 往往需要数十到数百纳秒，相当于数百个 CPU 周期。

所以取指和 Load 通常先查询 Cache：

L1 Cache → L2 Cache → Last-Level Cache → DRAM

指令本身也要从内存层次取得。常见核心具有 L1 Instruction Cache 与 L1 Data Cache。没有指令 Cache，前端连下一批机器码都可能来不及读取。

一次简单 add 如果操作数已经在寄存器中，可能极快；如果必须等待 DRAM，真正耗时的不是 ALU 加法，而是数据到达。

一次 Load 实际发生什么

指令：

mov rax, [rdi]

概念路径是：

  1. 地址生成单元计算虚拟地址；
  2. TLB 查找虚拟页到物理页的转换；
  3. 未命中时进行 Page Table Walk；
  4. 地址合法且页面存在后查询 L1 Data Cache；
  5. 未命中继续查 L2、L3；
  6. 再未命中则访问内存控制器和 DRAM；
  7. Cache Line 被带回，所需字节写入目标寄存器。

如果页表标记页面不存在，还会触发 Page Fault，内核可能需要从文件或 Swap 读取页面。此时延迟从纳秒级跃升到微秒甚至毫秒级。

多核不是一个更快的单核

每个 CPU Core 有自己的执行前端、寄存器状态和通常私有的 L1/L2 Cache。多个核心可以同时运行不同线程。

共享内存带来一致性问题：

Core 0 的 Cache 中有 x=1
Core 1 要写 x=2

Cache Coherence Protocol 协调 Cache Line 的所有权和状态。原子指令与内存屏障则为软件提供同步语义。

所以线程间共享一个变量不仅是“两个 CPU 读同一内存地址”，还涉及各核心 Cache、乱序执行和语言内存模型。

CPU 不理解“这一行代码”

下面一行：

total += prices[i];

可能变成：

计算数组地址
→ 从内存 Load
→ 整数或浮点 Add
→ 更新循环索引
→ 比较边界
→ 条件跳转

优化后也可能一次向量加载多个价格，用 SIMD 同时相加；若 total 最终无人使用，整段代码甚至会消失。

源代码行是人类组织逻辑的单位，CPU 的执行单位是 ISA 指令，微架构内部的调度单位又可能是 Micro-op。

用工具看到不同层

编译并查看：

cc -O2 -c add.c -o add.o
objdump -d -Mintel add.o

查看原始字节：

objdump -s add.o

统计硬件事件：

perf stat ./app

在支持的 Linux 环境中，perf stat 可以给出：

  • instructions；
  • cycles；
  • branches；
  • branch-misses；
  • cache-misses。

instructions / cycles 可以帮助理解吞吐，但不能单独解释全部性能。同样的指令数可能因内存访问模式不同而相差巨大。

最终答案：CPU 执行的是状态转换

CPU 眼中的程序不是源文件，也不是函数列表。它是：

当前指令地址所指向的机器码
+ 寄存器中的值
+ 地址空间中的字节
+ ISA 定义的状态转换规则

现代 CPU 为了更快实现这些规则，会预测、预取、乱序、并行和缓存。但无论内部怎样复杂，退休后的结果必须符合软件看到的指令集语义。

所以从“一行加法”走到底层，真正发生的是：编译器把高级语义降低为机器指令，操作系统让指令和数据出现在某个地址空间，CPU 再把字节解码为微操作，让寄存器、ALU、Cache 和内存共同推动状态向前。
