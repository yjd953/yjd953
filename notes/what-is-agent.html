01.01 / Agent foundations / ZH

Agent 到底是什么？

从 LLM 生成答案到闭环行动，找到“调用工具的 LLM”和 Agent 的真正分界线。

很多介绍会把 Agent 定义成“能够感知环境、规划并采取行动的智能体”。这句话没有错，却很难帮助工程师判断眼前的系统究竟是不是 Agent。

更有效的办法，是先看两个几乎相同的程序。

从 LLM → Answer 开始

第一个程序只有一次模型调用：

用户问题
  ↓
Prompt + LLM
  ↓
文本答案

用户问“北京明天会下雨吗”，模型根据训练参数和输入文本生成一段回答。它可能知道气候常识，却不知道明天的实时天气。无论回答看起来多聪明，程序都只完成了从输入文本到输出文本的映射。

这里没有行动，也没有新的事实进入系统。模型生成的“我查询了天气”只是一串文字，和真的查询天气不是一回事。

第二个程序允许模型请求工具：

用户问题
  ↓
LLM 生成 tool_call(search_weather, {city: "北京"})
  ↓
Runtime 执行工具
  ↓
Observation: 明日降水概率 70%
  ↓
LLM 根据新事实生成答案

关键变化并不是多了一个 API，而是系统形成了一个闭环：模型的输出可以改变下一轮输入，外部世界的结果也能反过来修正模型的判断。

模型没有真的“调用”工具

所谓 Tool Calling，首先仍然是生成。模型输出一段结构化数据：

{
  "name": "search_weather",
  "arguments": {
    "city": "北京",
    "date": "tomorrow"
  }
}

它没有建立网络连接，也没有执行 Python 函数。真正完成这些工作的，是模型之外的 Runtime：

  1. 判断输出是不是工具请求；
  2. 在 Tool Registry 中查找 search_weather；
  3. 校验城市、日期和调用权限；
  4. 执行函数并处理超时；
  5. 把结果包装成 Observation；
  6. 决定是否再次调用模型。

因此，一个能生成 Tool Call 的 LLM 只是具备了表达行动意图的能力。只有当外部程序解释这种意图、执行动作并把结果送回去，行动链才成立。

Agent 不等于“LLM 加工具”

假设客服系统固定执行下面的流程：

提取订单号 → 查询订单 API → 让 LLM 润色结果

即使中间使用了 Tool Calling，这仍然更像一条传统工作流。工具、顺序和停止条件都由程序员预先写死，模型只负责局部参数提取和文本生成。

再看另一个系统：

目标：找出订单延迟原因并给出处理方案

模型可选择：
- 查询订单
- 查询物流
- 查询库存
- 创建补偿单
- 请求人工确认

模型先查订单，看到“仓库未出库”；再查库存，发现缺货；随后判断补偿需要用户确认，于是暂停并提问。这里的下一步不是预先固定的，而是由模型根据当前 Observation 决定。

两者的边界不在于“有没有工具”，而在于：

系统是否把一部分运行时控制流交给模型，让模型依据中间结果决定下一步行动。

这种控制权不是无限自治。生产系统仍会用权限、预算、状态机和人工审批约束模型。Agent 的核心不是“想做什么就做什么”，而是在受控边界内动态选择行动。

五个部分，其实是五种责任

Agent、Tool、Memory、Planning、Environment 经常被画成五个方框。比记方框更重要的是理解它们各自承担什么责任。

Agent：维护目标并选择下一步

狭义的 Agent 是决策者：读取目标、当前状态和可用动作，产生下一步决策。工程语境里，人们也常用 Agent 指整个系统，包括模型和 Runtime。讨论架构时最好明确是哪一种含义。

Tool：把意图变成受控能力

Tool 是 Runtime 暴露给模型的动作接口。它把真实系统中的搜索、数据库、浏览器或支付能力包装成带名称、参数 Schema 和返回值的契约。

工具不是越多越好。描述重叠会让选择变难；权限过大会放大错误；返回内容太长会污染 Context。Tool 设计本身就是 Agent 行为设计。

Memory：让过去重新进入当前决策

模型调用结束后不会自动保存任何东西。所谓 Memory，是外部系统把历史对话、用户偏好、任务摘要或检索结果存下来，并在未来某一轮重新放入 Context。

因此 Memory 不是模型脑中永久存在的记忆，而是“存储、检索、选择、注入”四个动作组成的数据通路。

Planning：把远目标变成可执行的下一步

Planning 不一定是一份漂亮的计划文本。它可以是：

  • 模型一次性生成步骤列表；
  • 每轮只决定下一步的 ReAct；
  • Runtime 管大阶段，模型选小动作；
  • 执行失败后重新规划。

计划的价值不在“写出来”，而在于帮助系统管理依赖、预算和完成条件。

Environment：动作产生真实后果的地方

Environment 是 Agent 所处的外部世界：文件系统、网页、数据库、代码仓库、企业服务，甚至与它对话的人。

Observation 是 Environment 被 Runtime 转换后的局部视图。网页有几兆字节，模型通常只看到提取后的文本；数据库有上亿行，模型只看到查询结果。Agent 从来不是直接看见世界，而是看见 Runtime 允许它看见的表示。

判断边界的三个问题

面对一个“AI 自动化”系统，可以连续问三个问题。

1. 下一步由谁决定？

如果每一步都写在固定 DAG 中，模型只填参数，它更接近 AI Workflow。若模型能根据中间结果在多个合法动作中选择，Agent 性更强。

2. 中间结果会不会改变控制流？

调用搜索后无论结果如何都直接总结，只是工具增强生成。若“没搜到”会触发改写查询，“权限不足”会转人工，“证据冲突”会继续验证，系统才真正形成反馈循环。

3. 谁定义停止？

脆弱的 Demo 通常让模型说“完成”就结束。可靠 Agent 会同时检查模型决策和外部条件：目标是否满足、关键副作用是否核验、轮次与成本是否超限、是否需要人工确认。

一个更工程化的定义

可以把 Agent 写成一个有状态的转移过程：

(Goal, State, Observation, Available Actions)
                    ↓ model decides
                 Action
                    ↓ runtime executes
        (New State, New Observation)

只要目标尚未完成，这个过程就可能继续。模型负责从候选动作中做语义决策；Runtime 负责保证动作真的、合法地、可追踪地发生。

这也解释了为什么同一个 LLM 可以被做成聊天机器人，也可以被做成代码 Agent。模型能力没有凭空改变，改变的是它外面的程序：是否保存状态，是否提供工具，是否形成反馈，是否允许多轮决策。

Agent 的能力来自闭环，可靠性来自边界

Agent 并不是一个神秘的新模型。它首先是一种系统组织方式：

模型提出行动
→ Runtime 执行行动
→ 环境返回事实
→ 模型基于事实继续决策

闭环让模型能够行动，也让错误从“说错一句话”升级成“做错一件事”。所以 Agent 工程最重要的两件事必须同时成立：

  1. 给模型足够的反馈，使它能根据真实结果调整行为；
  2. 给 Runtime 足够的控制，使错误行动被校验、限制、取消和追踪。

“调用工具的 LLM”与“Agent”之间没有一条由产品名称决定的绝对分界线。更准确的判断是看：模型获得了多少控制流决策权，系统形成了多完整的观察与行动闭环，以及 Runtime 是否为这份决策权建立了可靠边界。
