Agent Loop：AI 为什么能够自己行动？

沿着 Think、Act、Observe、Think 跟踪一次任务，分清模型决策和 Runtime 执行。

语言模型一次只能完成一次推理调用：读取输入，生成输出，然后结束。它不会在 API 返回后自己再次醒来，也不会真的打开网页、修改文件。

Agent 看起来能够连续行动，是因为模型外面有一个循环不断做四件事：

Think → Act → Observe → Think

其中 Think 和动作选择由模型完成，Act 的执行、Observe 的构造以及整个循环的生命周期由 Runtime 完成。

跟踪一个完整任务

假设用户提出：

找出仓库中测试失败的原因，修复后重新运行相关测试。

Agent 可用的工具有：

  • list_files
  • read_file
  • search_code
  • apply_patch
  • run_tests

任务开始时，Runtime 建立状态：

{
  "goal": "定位并修复测试失败",
  "status": "running",
  "step": 0,
  "changed_files": [],
  "test_results": [],
  "budget": {
    "max_steps": 20,
    "deadline_seconds": 300
  }
}

第 1 轮：从目标到动作

Runtime 把用户目标、工具描述和必要上下文发给模型。模型并没有看到完整仓库，只知道有哪些工具可以用。

模型返回：

{
  "name": "run_tests",
  "arguments": {
    "target": "tests/test_price.py"
  }
}

这一步常被称作 Think，但工程上不要依赖模型暴露完整思维链。真正需要保存的是决策结果及其上下文：它选择了哪个工具、参数是什么、基于哪个模型版本、消耗了多少 Token。

第 2 轮：Runtime 执行动作

Runtime 收到 Tool Call 后依次完成：

  1. 确认 run_tests 存在；
  2. 校验 target 参数；
  3. 检查目标路径是否在工作区内；
  4. 分配 60 秒超时；
  5. 启动测试进程；
  6. 捕获退出码、标准输出和标准错误。

模型只表达“运行测试”的意图。进程管理、路径隔离和超时都不是模型完成的。

工具返回：

{
  "ok": false,
  "exit_code": 1,
  "summary": "expected 1990, got 19.9",
  "location": "tests/test_price.py:42"
}

第 3 轮：Observation 不是原始世界

Runtime 不一定把十万行日志原样塞给模型。它会截断无关输出、保留错误栈和退出码，再构造成 Observation。

这一步非常关键。模型只能依据它看到的 Observation 决策：

  • 如果省略了退出码，它可能把 Warning 当失败；
  • 如果截断了最前面的根因，它可能只看到后续连锁错误；
  • 如果工具把异常包装成普通文本，它可能误以为执行成功。

Observation 是 Runtime 对环境的编码，不是环境本身。

第 4 轮：反馈改变下一步

新的 Observation 被追加到 Context。模型看到金额差了 100 倍，决定搜索价格转换逻辑：

{
  "name": "search_code",
  "arguments": {
    "query": "price_cents",
    "path": "src"
  }
}

搜索结果指向 src/price.py。下一轮模型读取文件，发现代码在入库时已经除以 100，展示时又除了一次。随后它生成补丁请求。

Runtime 在真正修改前可以增加策略检查：

  • 只允许修改当前仓库；
  • 禁止修改依赖锁文件；
  • 补丁必须能干净应用；
  • 高风险目录需要人工确认。

补丁应用后，模型再次调用测试。测试通过并不自动等于任务完成，Runtime 还可以要求验证：

{
  "goal_satisfied": true,
  "evidence": {
    "tests_passed": 12,
    "tests_failed": 0,
    "changed_files": ["src/price.py"]
  }
}

最后模型根据这份事实生成给用户的总结。

Loop 中究竟循环了什么

可以把每轮抽象为状态转移：

Sₜ = 当前状态 + 当前 Context + 最新 Observation

模型：Sₜ → Decisionₜ
Runtime：Decisionₜ → Effectₜ + Observationₜ₊₁

下一轮不是对同一个 Prompt 重试，而是在新状态上重新决策。搜索结果、错误信息、文件改动和剩余预算都会改变后续路径。

如果 Observation 不进入下一轮，系统只是连续调用工具；如果 State 不随动作更新，系统会忘记已经做过什么；如果没有停止条件，循环就可能永远继续。

模型负责决策，Runtime 负责事实

两者的边界可以这样划分：

问题 模型 Runtime
下一步哪个动作最有意义 负责 提供候选与约束
工具参数是否符合 Schema 可能自检 必须校验
函数是否真的执行 不负责 负责
文件是否已修改 只能依据结果判断 负责记录与核验
是否超过预算 可以参考 必须强制
失败是否可重试 可以建议 按策略决定
高风险动作是否授权 不能自行授权 必须拦截
最终结果是否有证据 可以总结 必须提供事实

一个常见错误，是让模型同时扮演裁判和运动员。模型说“文件已经修改”“邮件已经发送”，系统便直接相信。可靠 Runtime 要依据工具结果或外部查询确认副作用，而不是把自然语言声明当事实。

Agent Loop 与 Event Loop 有什么相似

传统 Event Loop 也在重复：

等待事件 → 分发处理器 → 执行回调 → 等待下一事件

例如 Node.js Runtime 根据事件类型查找确定的回调：

socket readable → onReadable
timer expired   → onTimeout

Agent Loop 与它有三个共同点：

  1. 都由 Runtime 持有循环，而不是业务回调自己持有；
  2. 都把外部结果转成事件或 Observation；
  3. 都需要调度、超时、取消和错误隔离。

但两者的分发机制根本不同。

传统 Event Loop 的路由通常由代码确定：某种事件映射到某个处理器。Agent Loop 的路由由概率模型结合语义动态决定：相似的输入可能选择不同工具，同一个错误也可能产生不同修复路径。

因此：

Event Loop = 确定性调度器 + 预定义回调
Agent Loop = 确定性运行边界 + 概率性决策器

Agent Runtime 不能因为模型具有推理能力，就放弃传统 Runtime 的职责。恰恰因为决策不确定，外层调度必须更严格。

三种常见 Loop 结构

ReAct：每轮决定一个动作

观察 → 选一个工具 → 执行 → 再观察

优点是能快速利用新信息，适合探索和调试。缺点是模型调用次数多，容易绕圈。

Plan and Execute：先计划再执行

生成计划 → 执行步骤 1..N → 必要时重规划

它适合依赖关系明确的长任务，但早期错误计划可能把后续全部带偏。计划必须允许根据 Observation 修正。

Workflow + Agent：外层确定，局部开放

固定阶段 A → Agent 子任务 → 审批 → 固定阶段 B

生产系统常采用这种混合方式。合规、支付、发布等关键阶段由状态机控制；信息收集和故障分析等开放问题交给模型。

Agent 性并不是越强越好。模型只应获得解决不确定问题所需的最小控制权。

停止条件也是 Loop 的一部分

一个完整循环至少要处理五类终止：

  1. 成功：目标满足且关键结果已验证；
  2. 失败：出现不可恢复错误；
  3. 超限：达到轮次、Token、费用或时间预算；
  4. 取消：用户或上游系统终止任务；
  5. 暂停：等待授权、补充信息或人工确认。

只让模型输出 final_answer 作为停止条件是不够的。模型可能过早宣布完成，也可能反复尝试。Runtime 应拥有最终终止权，并把结束原因写入状态。

自主行动不是魔法

AI 看起来能自己行动，是三个条件同时成立的结果：

  • 模型能根据语义选择下一步；
  • Runtime 能把选择变成真实操作；
  • Observation 能回到下一轮，改变新的选择。

模型提供开放环境中的决策能力，循环提供持续性，Runtime 提供现实约束。任何一部分缺失，系统都会退化：只有模型，是一次性回答；只有 Runtime，是固定工作流；没有可靠 Observation，是在错误世界模型上持续行动。

所以理解 Agent 的第一步，不是研究它“想了什么”，而是完整追踪一次：

谁产生决策？
谁执行动作？
谁记录事实？
谁决定继续或停止？

这四个问题回答清楚，Agent 的自主性就从拟人化描述变成了可以实现、测试和调试的程序结构。
