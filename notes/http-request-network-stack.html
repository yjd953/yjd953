02.13 / Network stack / ZH

一个 HTTP 请求是怎么跑到服务器的？

沿 HTTP、TCP、IP、Ethernet、NIC、Router 与 Internet 解释每一层增加的信息。

先看一段最简单的 HTTP/1.1 请求：

GET /users/42 HTTP/1.1
Host: api.example.com
Accept: application/json
Connection: keep-alive

它是应用层能够理解的文本，但网卡不会解析 GET，路由器也不知道 /users/42 是什么。要把这些字节送到服务器，请求必须逐层进入网络栈：

HTTP
↓
TCP
↓
IP
↓
Ethernet / Wi-Fi
↓
NIC
↓
Switch / Router / Internet

每层都不只是“套一层壳”。它会增加这一层完成任务所需的信息：

HTTP:     请求哪个资源、执行什么操作
TCP:      属于哪个进程、字节处于什么位置、是否已确认
IP:       最终从哪台主机到哪台主机
Ethernet: 当前链路上交给哪个下一跳
NIC:      如何把内存中的帧变成物理信号

本文先用明文 HTTP/1.1 over TCP、IPv4、Ethernet 建立主线，再说明 HTTPS、HTTP/2、HTTP/3、Wi-Fi 和隧道会改变哪些部分。

请求最初只是一串用户态字节

应用可能通过库构造请求：

req, _ := http.NewRequest("GET", "http://api.example.com/users/42", nil)
resp, err := http.DefaultClient.Do(req)

在线路上不会出现 Go 的 http.Request 对象。库最终把请求编码成协议字节。HTTP/1.1 大致是：

47 45 54 20 2f 75 73 65 72 73 2f 34 32 20 ...
 G  E  T     /  u  s  e  r  s  /  4  2

请求行和 Header 以 CRLF 分隔，Header 区域以空行结束：

GET /users/42 HTTP/1.1\r\n
Host: api.example.com\r\n
Accept: application/json\r\n
\r\n

若请求有 Body，HTTP 还要说明其边界，例如通过 Content-Length 或 HTTP/1.1 Chunked Transfer Coding。

HTTP 层解决：

  • Method 是 GET、POST 还是其他操作；
  • Target 是哪个路径和 Query；
  • 请求属于哪个 Host；
  • Body 用什么媒体类型编码；
  • 缓存、认证、内容协商等语义。

它不负责选择网卡，不保证包不丢，也不知道 MAC 地址。

write() 把字节交给 Socket，不是交给网卡

客户端已经建立 TCP Socket 后，HTTP 库最终会执行类似：

ssize_t n = write(socket_fd, request, request_len);

或者 send()、writev() 等接口。

系统调用让内核根据文件描述符找到 Socket。一般情况下，内核把用户数据复制或引用到 Socket 的发送缓冲区，然后返回。此时：

  • 数据可能还没离开主机；
  • 甚至还没被切成最终线上 TCP Segment；
  • write() 成功不等于服务器应用已经收到；
  • 它通常只表示本机内核接受了这些字节。

Blocking Socket 的 write() 也不是“等到网络发完才返回”。它可能在发送缓冲区空间不足时阻塞；Non-blocking Socket 则可能返回 EAGAIN。具体复制、聚合与 Zero-Copy 路径取决于系统调用和内核实现。

TCP 增加进程复用和可靠字节流信息

TCP 接过一段连续字节流，根据 MSS、拥塞窗口、发送窗口以及实现策略组织 Segment。

典型 TCP Header 包含：

Source Port
Destination Port
Sequence Number
Acknowledgment Number
Data Offset
Flags
Window Size
Checksum
Urgent Pointer
Options

端口把数据送到正确 Socket

假设连接是：

192.168.1.20:53142 → 203.0.113.10:80

源端口 53142 是客户端临时端口，目标端口 80 是服务器监听端口。服务器收到包后，通过协议、地址和端口定位连接状态：

TCP + local IP:port + remote IP:port

IP 地址找到主机，端口再参与找到主机内的通信端点。把“端口等于进程”当成绝对关系并不准确：一个进程可持有多个端口；多个 Worker 也可能通过内核机制共享监听端口；已连接 Socket 依赖完整四元组区分。

Sequence Number 描述字节位置

TCP 是字节流，不保留应用一次 write() 的消息边界。

应用执行：

write("GET ")
write("/users/42 ...")

接收方可能一次 read() 得到全部，也可能分多次得到。反过来，一次大 write() 也可能被拆成多个 Segment。

序列号标记 Payload 第一个字节在发送字节流中的位置：

Segment A: seq=1001, len=1000
Segment B: seq=2001, len=460

接收方用序列号：

  • 检测缺口；
  • 重排乱序 Segment；
  • 丢弃重复数据；
  • 生成累计确认。

ACK 2461 表示：

我已连续收到 2460 及以前的字节，
下一步期待 2461。

SACK Option 可以额外报告不连续收到的区间，减少不必要重传。

Window 与拥塞控制不是一回事

TCP Header 中的接收窗口用于 Flow Control：

receiver advertised window
→ 接收方缓冲区还能接收多少

发送方还维护 Congestion Window：

cwnd
→ 网络目前大概能承受多少未确认数据

实际可发送的未确认数据受两者较小值等条件约束：

send limit ≈ min(rwnd, cwnd)

Flow Control 保护接收方，Congestion Control 保护网络。两者都影响 HTTP 数据何时被放到线上。

TCP Checksum 检查什么

TCP Checksum 覆盖 TCP Header、Payload，以及来自 IP 层的伪首部信息。它能检测传输中的许多比特错误，但不是密码学完整性保护，不能抵御主动篡改。

HTTPS 的 TLS AEAD 会提供更强的认证加密，但 TCP Checksum 仍参与传输层错误检测。

MSS 决定 TCP 一段通常装多少 Payload

常见 Ethernet MTU 是 1500 Bytes。若没有额外 Option：

1500 IP packet
- 20 IPv4 header
- 20 TCP header
= 1460 TCP payload

所以常见 TCP MSS 为 1460，但这不是全网常量：

  • IPv6 基础头为 40 Bytes；
  • TCP Timestamp 等 Option 增加 Header；
  • PPPoE、VPN、VXLAN 等封装降低可用空间；
  • Jumbo Frame 的 MTU 更大；
  • Path MTU 由整条路径上最小可承载单元限制。

MSS 通常在 SYN 中协商，表示对方希望收到的最大 TCP Payload 大小。TCP 尽量按 MSS 分段，避免依赖 IP Fragmentation。

一份 10KiB HTTP Body 不会对应“一个网络包”：

HTTP body
→ multiple TLS records, possibly
→ multiple TCP segments
→ multiple IP packets
→ multiple link frames

这些边界不保证一一对齐。

IP 增加端到端主机与路由信息

TCP Segment 被放入 IP Packet。IPv4 Header 的关键字段包括：

Version
Internet Header Length
Total Length
Identification / Flags / Fragment Offset
TTL
Protocol
Header Checksum
Source IP
Destination IP
Options, if any

Source 与 Destination 描述端到端地址

例如：

Source IP:      192.168.1.20
Destination IP: 203.0.113.10
Protocol:       6 (TCP)

目标 IP 让沿途路由器决定下一跳；Protocol=6 让目标主机知道 IP Payload 应交给 TCP。UDP 的 IPv4 Protocol Number 是 17。

经过 NAT 时，Source IP 和端口可能被改写，所以“端到端保持不变”要以没有 NAT、代理或隧道为前提。NAT 设备还必须同步更新相关 Checksum。

TTL 防止包永久循环

每经过一个三层路由器，IPv4 TTL 至少减一：

64 → 63 → 62 → ...

减到零时，路由器丢弃包，通常返回 ICMP Time Exceeded。traceroute 正是利用逐步增加 TTL/Hop Limit 来发现沿途路由节点。

TTL 不是“以秒计的精确生存时间”。在现代转发中，它实际表现为 Hop Count 上限。IPv6 直接把字段命名为 Hop Limit。

IP 不提供 TCP 那样的可靠性

IP 层尽力转发 Datagram，但允许：

  • 丢失；
  • 重复；
  • 乱序；
  • 路径变化。

IPv4 Header Checksum 只覆盖 IPv4 Header，不覆盖 Payload；IPv6 基础头没有 Header Checksum。可靠、有序字节流由 TCP 在端系统实现，而不是要求每台路由器维护每条 TCP 连接。

路由表决定下一跳，不决定完整路径

本机拿目标 IP 查询路由表，执行最长前缀匹配：

203.0.113.10
→ default route 0.0.0.0/0
→ gateway 192.168.1.1
→ interface en0

内核在当前时刻只需要知道：

从哪个接口发出
交给哪个下一跳
选择哪个源 IP

它通常不知道 Internet 上之后的完整路径。每台路由器独立重复路由查找。

若目标是同一子网：

192.168.1.50 is on-link
→ next hop is destination itself

若目标在远端：

203.0.113.10 is remote
→ next hop is gateway 192.168.1.1

Ethernet 增加当前链路的交付信息

IP Packet 进入 Ethernet Frame。常见字段：

Destination MAC
Source MAC
EtherType
Payload
Frame Check Sequence

示意：

Dst MAC:  router's MAC
Src MAC:  client's NIC MAC
EtherType: 0x0800 (IPv4)
Payload:   IPv4 packet
FCS:       link-level error detection

如果服务器远在 Internet，Destination MAC 为什么是路由器，而不是服务器？

因为 MAC 地址只在当前二层广播域内用于交付。客户端不能把本地 Ethernet Frame 直接横跨所有路由器送到服务器。它只把帧交给当前下一跳。

IP destination: 203.0.113.10
MAC destination: 192.168.1.1 对应的网关 MAC

内核通过 ARP 获得 IPv4 下一跳 MAC：

ARP Request:
Who has 192.168.1.1? Tell 192.168.1.20

ARP Reply:
192.168.1.1 is at aa:bb:cc:dd:ee:ff

IPv6 使用 ICMPv6 Neighbor Discovery。

FCS 与上层 Checksum 为什么并存

Ethernet FCS 检测当前链路上 Frame 的错误。路由器收到后会移除旧 Frame，并为下一链路生成新 Frame 和新 FCS。

TCP Checksum 是端到端传输层校验的一部分。不同层的校验覆盖范围和信任边界不同，所以不是简单重复：

Ethernet FCS: one link
IPv4 Header Checksum: current IPv4 header
TCP Checksum: end-to-end TCP segment + pseudo-header
TLS AEAD tag: cryptographic integrity and authenticity

一个包在离开主机前长什么样

假设 TCP Payload 是请求的一部分：

GET /users/42 HTTP/1.1\r\n...

逻辑封装为：

Ethernet Frame
├─ Ethernet Header
│  ├─ next-hop destination MAC
│  ├─ local source MAC
│  └─ EtherType = IPv4
├─ IPv4 Packet
│  ├─ source IP
│  ├─ destination IP
│  ├─ TTL
│  └─ Protocol = TCP
├─ TCP Segment
│  ├─ source port
│  ├─ destination port
│  ├─ sequence / acknowledgment
│  ├─ flags / window / options
│  └─ checksum
├─ HTTP bytes
└─ Ethernet FCS

术语随层变化：

HTTP message
TCP segment
IP packet / datagram
Ethernet frame
physical bits / symbols

日常常把它们都叫“包”，沟通方便，但调试时最好明确正在看哪一层。

NIC 如何把 Frame 变成物理信号

内核网络栈不会由 CPU 逐字节把 Frame 推到网线上。典型发送路径使用环形队列与 DMA：

1. Kernel prepares packet buffers
2. Driver fills TX descriptors
3. NIC reads descriptors
4. NIC DMA reads packet data from RAM
5. NIC performs configured offloads
6. PHY transmits electrical / optical / radio symbols
7. NIC reports completion

现代 NIC 可能承担：

  • TCP Segmentation Offload；
  • Checksum Offload；
  • VLAN Tag insertion；
  • 多队列发送；
  • Traffic Shaping；
  • 部分加密或隧道 Offload。

因此在发送主机上抓包时，可能看到一个大于 MTU 的“包”或未计算完成的 Checksum。这不一定是线上真的发送了非法 Frame，而可能是抓包点位于软件分段或硬件校验之前。

Switch 与 Router 做的事不同

二层交换机

交换机主要根据 Destination MAC 转发 Frame。它学习 Source MAC 出现在哪个端口，形成 MAC Address Table：

aa:bb:... → port 3
cc:dd:... → port 7

未知单播、广播等流量可能在 VLAN 内 Flood。交换机通常不因普通二层转发而修改 IP TTL。

三层路由器

路由器接收发给自己的链路层 Frame：

remove incoming Ethernet header/trailer
→ inspect IP destination
→ decrement TTL
→ route lookup
→ possibly apply ACL/NAT/QoS
→ create new outgoing link frame

下一跳 Frame 的 MAC 地址会变化：

Client → Home Router:
  src MAC = client
  dst MAC = home router

Router → ISP next hop:
  src MAC = router outgoing interface
  dst MAC = ISP next hop

原始 HTTP 字节通常不会被普通 IP 路由器理解或重写，但代理、防火墙、NAT、中间盒和 TLS 终止设备可能处理更高层。

Internet 不是一台巨型路由器

Internet 由多个 Autonomous System 互联：

home network
→ access ISP
→ transit / peering
→ destination network
→ data-center edge

BGP 在 AS 之间传播“哪些 IP Prefix 可通过哪里到达”。每个网络根据策略选择路径，策略不只考虑地理最短距离。

单个 IP Packet 逐跳转发。沿途设备可能：

  • 排队；
  • 因拥塞丢弃；
  • 改选其他等价路径；
  • 执行 NAT 或防火墙策略；
  • 进入 MPLS、GRE、IPsec、VXLAN 等封装；
  • 因 MTU 问题返回 ICMP。

TCP 从 ACK、丢包和 RTT 变化推断网络状态，并调整发送速率。HTTP 应用不需要直接控制每台路由器。

服务器端发生逐层解封装

服务器 NIC 收到 Frame：

physical signal
→ NIC validates frame
→ DMA to receive buffer
→ driver / polling
→ Ethernet layer
→ IP layer
→ TCP layer
→ Socket receive queue
→ application read()

每一层根据自己的字段决定下一步：

EtherType 0x0800  → IPv4 handler
IP Protocol 6     → TCP handler
destination tuple → matching TCP socket
TCP sequence      → reorder into byte stream
HTTP parser       → request line, headers, body

如果目标端口没有监听 Socket，主机通常回复 TCP RST。若防火墙静默丢弃，客户端可能只看到超时。两者都表现为“访问失败”，但协议证据不同。

已建立连接的数据到达后，TCP 先按序放入 Socket 接收缓冲区，再唤醒或通知应用。应用调用 read() 得到的是字节流，不会直接看到 IP Header 或 Ethernet Header。

服务器应用如何找出完整 HTTP 请求

TCP 不保存消息边界，所以 HTTP Parser 必须自己识别：

request line ending
headers ending
body length or transfer coding

一次 read() 可能只得到：

GET /users/

下一次才得到：

42 HTTP/1.1\r\nHost: ...

健壮的服务器不能假设一次读取等于一次请求。它要维护 Parser State，并限制请求行、Header 数量和 Body 大小，防止 Slowloris、内存耗尽和解析歧义。

HTTP/1.1 Keep-Alive 允许同一 TCP 连接承载多个顺序请求。HTTP/2 通过 Stream ID 在一个连接中多路复用。HTTP/3 的流由 QUIC 提供。

HTTPS 在哪里插入

真实 Web 流量通常是：

HTTP
↓
TLS
↓
TCP
↓
IP
↓
Link

HTTP/1.1 文本或 HTTP/2 Frame 先被 TLS 封装成 Record 并加密。网络中间设备能观察的通常包括：

  • IP 地址和端口；
  • 包长与时序；
  • 一部分握手元数据，具体取决于 TLS 版本和 ECH；
  • 不能直接读取加密后的 HTTP Path、Header 与 Body。

TLS Record 边界也不等于 TCP Segment 边界：

one TLS record → multiple TCP segments
multiple small TLS records → one observed packet after coalescing

HTTP/3 的层次不同：

HTTP/3 Frames
→ QUIC Streams + TLS protection
→ UDP Datagrams
→ IP Packets
→ Link Frames

此时 TCP Header 不存在，可靠性、拥塞控制和流复用由 QUIC 在端系统用户态或内核辅助下实现。

封装不是简单俄罗斯套娃

教科书图很有用，但真实系统还有几个重要例外。

分段与重组改变边界

一个 HTTP Message 可跨多个 TCP Segment。一个应用 write() 也不对应固定 Segment。接收侧最终只还原有序字节流。

Offload 改变观察点

抓包工具可能在 NIC 分段前或合并后看到数据，因此抓包里的大小、Checksum 和包数不一定等于物理线路。

隧道会再次封装

VPN 或数据中心 Overlay 可能形成：

Outer Ethernet
└─ Outer IP
   └─ UDP / tunnel header
      └─ Inner Ethernet
         └─ Inner IP
            └─ TCP
               └─ HTTP

“IP Header 只有一个”并不总成立。

Loopback 可能没有 Ethernet

请求 127.0.0.1 时，数据可在内核 Loopback 路径中交付，不经过物理 NIC 和普通 Ethernet 链路。用本地抓包理解 TCP/HTTP 很方便，但不能据此推断物理网卡路径。

用实验看见各层

为了能看到 HTTP 明文，可在自己的机器上使用本地 HTTP 服务。

启动服务：

python3 -m http.server 8080

发送请求：

curl -v http://127.0.0.1:8080/

抓包：

Linux：

sudo tcpdump -i lo -nn -A 'tcp port 8080'

macOS：

sudo tcpdump -i lo0 -nn -A 'tcp port 8080'

-A 会把可打印 Payload 显示为文本，可观察：

GET / HTTP/1.1
Host: 127.0.0.1:8080
User-Agent: curl/...
Accept: */*

Loopback 没有展示真实以太网链路。若要观察局域网 Frame，可对自己控制的远端 HTTP 服务，在实际接口抓取并显示链路头：

sudo tcpdump -i en0 -nn -e -X 'host <server-ip> and tcp port 8080'

只应抓取有权限分析的流量。

分别观察邻居和路由

Linux：

ip route get <server-ip>
ip neigh show

macOS：

route -n get <server-ip>
arp -an

观察路径

traceroute <server-ip>

某些节点不回复或被防火墙过滤时会显示 *。这不等于数据无法经过该节点；它只表示没有收到匹配的探测响应。

每层究竟增加了什么

层 主要增加的信息 作用范围 核心问题
HTTP Method、Target、Header、Body 边界 Client 与 HTTP Server/Proxy 要做什么
TLS 身份、加密套件、Nonce、认证标签 TLS 两端 如何保密且防篡改
TCP Port、Sequence、ACK、Window、Flags TCP 两端 如何交付可靠字节流
IP Source/Destination IP、TTL、上层协议 跨多个网络 最终送到哪台主机
Ethernet Source/Destination MAC、EtherType、FCS 当前二层链路 下一跳交给谁
NIC/PHY Descriptor、队列与物理编码 主机到链路 如何真正发送比特

“上层依赖下层”不代表下层知道上层语义。路由器能转发承载 HTTP 的 IP Packet，却不需要理解 GET；TCP 能可靠传输 TLS 密文，却不知道里面是 JSON 还是图片。

最终答案

一个 HTTP 请求跑到服务器，不是同一个对象原封不动地穿过六层。应用的 HTTP 字节被 TCP 编入一个有序字节流，被 IP 放进可路由的数据报，再被当前链路封装成 Frame。NIC 把 Frame 变成物理信号；每台路由器移除入站链路封装、查询目标 IP，再为下一跳建立新的链路封装。

到达服务器后，过程反向进行：网卡收帧，IP 找到 TCP，TCP按序重组字节并找到 Socket，HTTP Parser 才重新看到请求的 Method、Path、Header 与 Body。

最关键的边界是：

HTTP 负责语义
TCP 负责端到端字节流
IP 负责跨网络寻址
Ethernet / Wi-Fi 负责当前链路交付
NIC 负责物理收发
Router 负责逐跳选择下一段路径

每一层都增加恰好足够本层完成任务的信息。所谓“网络请求”，正是这些独立机制在同一批字节上的协作结果。
