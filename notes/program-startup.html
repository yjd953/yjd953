02.01 / Program loading / ZH

一个程序启动的时候，操作系统到底做了什么？

从 ./app 追踪 fork、exec、ELF、Loader、虚拟内存、动态链接，直到 main 真正执行。

在 Linux 终端输入：

./app

看起来只是“运行一个文件”。实际上，从按下回车到 main() 第一条语句之间，Shell、内核、ELF Loader、虚拟内存系统、动态链接器和 C Runtime 已经完成了一串精密交接。

下面以 Linux x86-64 上的动态链接 ELF 程序为主线。不同操作系统和静态链接程序细节不同，但职责分层相近。

第 0 步：Shell 先把命令变成一次执行请求

终端程序只负责收发字符。真正解析 ./app 的通常是 Bash、Zsh 等 Shell。

Shell 先完成：

  1. 词法解析，识别命令名和参数；
  2. 展开变量、通配符、重定向与管道；
  3. 判断它是内建命令、函数还是外部程序；
  4. 为前台或后台任务设置进程组；
  5. 准备标准输入、输出和错误。

./app 带有斜杠，因此 Shell 不搜索 PATH，直接使用当前目录下的 app。内核随后检查路径是否存在、是否为普通文件、当前用户是否具有执行权限，以及挂载点是否带有 noexec。

传统 Unix 心智模型是：

Shell
  ├─ fork() 复制出子进程
  └─ 子进程 execve("./app", argv, envp)

fork() 后父子进程看似拥有同一份内存，内核通常通过 Copy-on-Write 共享物理页；只有一方写入时才复制。父 Shell 留在原程序中等待，子进程准备变成 app。

现代 Shell 也可能使用 vfork()、posix_spawn() 或内部优化，但最终都要触发类似 execve 的内核装载路径。

第 1 步：execve 不是创建新进程

一个常见误解是 execve() “启动了新进程”。更准确地说：

fork 创建新的进程身份，execve 用新程序替换当前进程的用户态映像。

调用：

execve("./app", argv, envp);

成功后不会返回。子进程的 PID 通常不变，但原来的：

  • 代码段；
  • 数据段；
  • 用户栈；
  • 大部分内存映射；
  • 线程；
  • 信号处理函数；

会被新程序替换或重置。

并非所有资源都消失。没有设置 FD_CLOEXEC 的文件描述符会跨 exec 保留，这正是 Shell 实现重定向和管道的基础：

./app > output.txt

Shell 可以先让子进程把文件绑定到描述符 1，再执行 app。新程序一启动，自己的标准输出已经指向该文件。

第 2 步：内核识别 ELF

内核读取文件开头。Linux 可执行文件通常是 ELF，前四字节为：

7f 45 4c 46
 .  E  L  F

ELF Header 告诉内核：

  • 32 位还是 64 位；
  • 大端还是小端；
  • 目标指令集；
  • 文件类型是可执行文件还是位置无关可执行文件；
  • 程序入口地址；
  • Program Header Table 在哪里。

真正指导装载的是 Program Header，而不是链接器和调试器常看的 Section Header。Program Header 中的 PT_LOAD 描述哪些文件区间要映射到进程地址空间，以及它们需要读、写还是执行权限。

可以观察：

readelf -h ./app
readelf -l ./app

典型映射大致是：

文件中的代码和只读数据 → r-x / r-- 映射
已初始化全局变量       → rw- 映射
BSS                     → 匿名零页

权限分离很重要。采用 W^X 原则时，同一页不应同时可写和可执行，降低代码注入风险。

第 3 步：建立新的虚拟地址空间

进程看到的是虚拟地址，不是直接拿到一段连续物理内存。内核为新进程准备页表和内存区域描述：

高地址
┌──────────────────────┐
│ Kernel space         │  用户态不可直接访问
├──────────────────────┤
│ Stack                │  通常向低地址增长
├──────────────────────┤
│ mmap area            │  共享库、匿名映射、文件映射
├──────────────────────┤
│ Heap                 │  传统上向高地址增长
├──────────────────────┤
│ BSS / Data           │
├──────────────────────┤
│ Read-only / Text     │
└──────────────────────┘
低地址

这只是典型布局，具体地址受架构、PIE、ASLR 和内核策略影响。

此时“映射 2MB 代码”不等于立即从磁盘读入 2MB，也不等于立即分配 2MB 物理页。内核主要建立虚拟内存区域。真正访问某页时，CPU 发现页表项不存在，触发 Page Fault，内核才把相应文件页读入或映射已有 Page Cache。

这叫 Demand Paging。它让大程序只为实际触达的页面付出内存和 I/O 成本。

第 4 步：Stack 是内核准备的启动信封

新程序不能从空白环境开始。内核在用户栈顶部写入初始数据：

argc
argv[0] = "./app"
argv[1] ...
NULL
envp[0] = "PATH=..."
envp[1] ...
NULL
auxiliary vector

Auxiliary Vector，简称 auxv，向用户态 Runtime 提供内核信息，例如：

  • Program Header 地址；
  • 页大小；
  • 真实与有效用户 ID；
  • 安全执行标志；
  • 随机数据地址；
  • vDSO 地址；
  • ELF 入口信息。

这就是 main(int argc, char **argv, char **envp) 参数的源头。但内核不会直接调用 main，它只把寄存器和栈设置到 ABI 约定的初始状态，然后跳到 ELF 的入口地址。

第 5 步：如果是动态链接程序，先运行 Dynamic Linker

执行：

readelf -l ./app | grep INTERP

可能看到：

/lib64/ld-linux-x86-64.so.2

ELF 的 PT_INTERP 告诉内核：这个程序需要用户态动态链接器。于是内核不仅映射 app，还映射 ld-linux，并把控制权交给动态链接器的入口。

动态链接器需要：

  1. 读取主程序的动态段；
  2. 找到依赖库，如 libc.so.6；
  3. 按搜索规则定位这些共享对象；
  4. 用 mmap 把它们映射进地址空间；
  5. 处理符号解析与重定位；
  6. 初始化线程局部存储 TLS；
  7. 执行依赖库的初始化函数；
  8. 最终跳转到主程序入口。

可以查看依赖：

ldd ./app

但对不可信文件不要随意使用某些会执行装载逻辑的工具；更安全的静态检查可使用 readelf -d。

第 6 步：重定位把“名字”变成运行时地址

源代码调用 printf 时，编译器并不知道 libc 最终被 ASLR 放在哪个地址。

动态链接器根据符号表和重定位表修补引用。常见机制包括：

  • GOT：保存运行时解析出的地址；
  • PLT：为外部函数调用提供跳板；
  • Lazy Binding：第一次调用时再解析；
  • Eager Binding：启动时完成解析。

概念上：

call printf
  ↓
PLT entry
  ↓
GOT 中是否已有地址？
  ├─ 有：跳到 libc 的 printf
  └─ 无：动态链接器解析后写入 GOT，再跳转

现代编译和安全选项会改变具体路径，例如 PIE、RELRO、-fno-plt 或立即绑定，但核心任务不变：把编译期尚未确定的引用，连接到本次进程中的真实地址。

第 7 步：入口不是 main，而是 _start

ELF Header 中的入口通常指向 _start。它由 C Runtime 的启动代码提供，而不是普通 C 函数。

_start 所处环境还没有普通函数调用者。它要按照 ABI 取出内核准备的初始栈，完成必要对齐，然后调用类似：

__libc_start_main(
    main,
    argc,
    argv,
    init,
    fini,
    ...
)

运行时接着处理：

  • libc 初始化；
  • 线程与 TLS 基础设施；
  • 栈保护随机值；
  • 全局构造函数；
  • C++ 静态对象构造；
  • atexit 清理链；
  • 最终调用 main(argc, argv, envp)。

所以 main 只是语言层约定的入口，不是内核眼中的入口。

Heap 在什么时候出现

ELF 装载时，内核会建立数据段和 BSS，并维护传统 program break。用户看到的 Heap 通常由 Allocator 在运行时管理。

当 malloc 第一次需要更多空间时，Allocator 可能：

  • 通过 brk 扩展传统 Heap；
  • 通过 mmap 获取独立虚拟内存区域；
  • 直接复用此前保留的空闲块。

因此程序开始时地址空间中可以有“Heap 区域概念”，但并不意味着已经为未来所有动态对象分配了物理内存。

CPU 终于从哪里开始

内核完成装载后，把当前线程的用户态指令指针设置为入口地址，栈指针设置为新栈顶部，然后从内核态返回用户态。

CPU 接下来取到的第一条用户指令属于：

  • 动态链接器入口，如果程序动态链接；
  • 程序 _start，如果静态链接或动态链接器已交接。

最终链路是：

键盘回车
→ Terminal 将字符交给 Shell
→ Shell 解析 ./app
→ fork / posix_spawn
→ execve
→ 内核校验并解析 ELF
→ 建立虚拟地址空间
→ 映射程序段、Stack、vDSO
→ 启动 Dynamic Linker
→ 映射共享库并重定位
→ 跳到 _start
→ C Runtime 初始化
→ main

用工具验证，而不是只背流程

可以准备：

#include <stdio.h>

int main(int argc, char **argv) {
    printf("pid started, argv[0]=%s\n", argv[0]);
    return 0;
}

然后观察：

gcc -O0 -g app.c -o app
file ./app
readelf -h -l -d ./app
strace -f ./app
cat /proc/$(pidof app)/maps

如果程序退出太快，可在 main 中暂时 sleep。/proc/<pid>/maps 会展示主程序、Heap、共享库、动态链接器、Stack 与 vDSO 的虚拟内存区域。

strace 看不到装载前所有内核内部步骤，因为它从系统调用边界观察；readelf 看文件结构；/proc 看运行时映射。三者拼起来，才接近完整事实。

“启动程序”其实是一次受控替换

./app 并不是把整个文件复制进内存，然后从 main 开始。更准确的描述是：

  1. Shell 建立一个合适的进程执行环境；
  2. execve 请求内核用 ELF 替换当前用户态映像；
  3. 内核建立虚拟地址空间和初始栈；
  4. 动态链接器补齐运行时依赖；
  5. C Runtime 把内核入口翻译成语言入口；
  6. 页面在真正访问时才逐步进入物理内存。

当 main() 开始时，这个进程已经携带 PID、页表、文件描述符、权限、信号状态、环境变量、共享库和运行时设施。代码第一行看似是起点，实际上是操作系统与语言 Runtime 完成交接后的终点。
