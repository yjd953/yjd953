Agent Harness：把模型变成可靠执行系统

NOTE 01 · RUNTIME ARCHITECTURE · 14 MIN READ · 2026

生产级 Agent 的核心，不是让模型“更会想”，而是让整个系统在不确定中仍然可控。Agent Harness 就是包围模型的执行内核：它组织上下文、约束决策、调度工具、持久化状态、核验结果，并把每次运行变成可回放的证据。

IN THIS NOTE1. Harness 的职责边界2. 六层运行时架构3. 用状态机代替无限循环4. 恢复优先的执行设计5. 上线检查表

1. Harness 的职责边界

如果把 Agent 简化为 LLM + Prompt + Tools，系统很快会遇到四类问题：上下文不可追踪、工具副作用不可控、失败后无法恢复、线上表现无法解释。Harness 的职责不是替模型做推理，而是把推理放进一个有边界、有状态、有证据的运行环境。

模型负责提出下一步；Harness 负责判断这一步是否允许、如何执行、执行后是否真的成功。
图 1 · 模型输出只是候选动作；Harness 持有执行权与系统状态。

2. 六层运行时架构

一个实用的 Harness 可以拆为六层。分层的价值不在“架构漂亮”，而在于每层拥有独立可测试的契约。

  1. Ingress：归一化用户请求、附件、会话身份和调用来源。
  2. Context Engine：检索、裁剪、排序并标注上下文来源，管理 token 预算。
  3. Decision Loop：让模型在限定动作空间中产生计划、工具调用或最终答复。
  4. Execution Plane：校验参数、检查权限、执行工具、处理超时与幂等。
  5. State Store：保存任务快照、证据、检查点、未决动作和恢复信息。
  6. Observability & Eval：记录轨迹并把线上失败转成可重复的回归用例。
图 2 · 六层架构把“智能”与“可靠执行”解耦。

3. 用状态机代替无限循环

最危险的 Agent 实现通常是一个开放式 while true：模型决定是否继续，系统没有步数、成本、时间和副作用边界。更稳健的方式是显式状态机。

RECEIVED → CONTEXT_READY → DECIDING → ACTION_PENDING
         → EXECUTING → VERIFYING → {DECIDING | COMPLETED | BLOCKED}

Global guards:
- max_steps
- deadline
- token_budget
- side_effect_budget
- human_checkpoint

每次状态转移都要记录：进入条件、输入摘要、决策依据、输出、错误类型和下一状态。这样系统才可以暂停、恢复、重放和审计。

4. 恢复优先的执行设计

失败不是异常边缘，而是分布式工具调用的日常。恢复设计至少包含三层：

  • Step retry：仅对瞬时错误重试，并使用指数退避和抖动。
  • Checkpoint resume：从最后一个已验证状态继续，而不是重新执行所有副作用。
  • Human resolution：权限、验证码、目标歧义或高影响动作进入明确的人工检查点。
关键不变量
恢复后不能重复已完成的外部动作；无法判断动作是否完成时，先读取权威状态，再决定继续、补偿或升级人工处理。

5. 上线检查表

  • 任务状态是否结构化并可序列化？
  • 每类循环是否有步数、时间、成本上限？
  • 每次外部动作是否有幂等策略和核验步骤？
  • 上下文条目是否携带来源、时间与可信度？
  • 中断后能否从已验证检查点恢复？
  • 轨迹是否足以回答“为什么做了这一步”？

结论：Harness 的成熟度决定 Agent 的工程上限。模型能力可以替换，但状态、边界、执行与学习闭环必须成为稳定底座。

Tool Protocol：让每次调用都像一笔可信交易

NOTE 02 · TOOL CONTRACTS · 12 MIN READ · 2026

工具调用是 Agent 从“生成文本”走向“改变世界”的分界线。一个可靠的 Tool Protocol，不只描述函数名和参数，还要定义权限、幂等、错误语义、副作用、核验与补偿。

IN THIS NOTE1. 工具调用的事务模型2. Schema 只是第一层3. 风险分级与授权4. 重试、幂等与核验5. 工具上线清单

1. 工具调用的事务模型

把一次工具调用视作七阶段事务，比把它当作“函数执行”更接近生产现实：

图 1 · 成功不是工具返回 200，而是目标状态被权威来源确认。

2. Schema 只是第一层

JSON Schema 可以约束结构，却不能完整表达业务语义。生产工具契约至少要包含：

  • Structural contract：字段类型、必填项、枚举、长度、格式。
  • Semantic contract：字段之间的约束，例如结束时间必须晚于开始时间。
  • Effect contract：会创建、更新、删除、发送或发布什么。
  • Error contract：区分可重试、不可重试、部分成功、权限不足和目标冲突。
  • Verification contract：执行后从哪里读取权威状态，什么条件算真正成功。
{
  "name": "create_task",
  "risk": "reversible_write",
  "idempotency": "required",
  "timeout_ms": 8000,
  "verify": "GET /tasks/{result.id}",
  "success": "status == active && title == request.title"
}

3. 风险分级与授权

工具权限不应是简单的 allow/deny。更可操作的是按“可逆性 × 影响范围 × 敏感度”分级。

图 2 · 风险越高，越需要显式授权、预览、确认和可审计证据。

对高影响动作，推荐“两阶段提交”体验：Agent 先准备完整输入和影响摘要，用户或策略引擎确认后再执行最终提交。确认必须绑定具体对象、动作和内容，不能用一次宽泛授权覆盖后续所有操作。

4. 重试、幂等与核验

只重试可重试错误

网络抖动、限流和临时不可用通常可重试；参数错误、权限不足、业务冲突不应盲目重试。错误类型必须进入协议，而不是埋在自然语言 message 中。

幂等优先于“聪明去重”

创建订单、发消息、提交审批这类动作应使用幂等键。键要绑定业务意图，而不是每次尝试随机生成。若下游不支持幂等，Harness 必须在重试前查询状态。

核验权威状态

工具返回的 success 只能证明请求被接受，不能证明业务结果已落地。核验应该读取独立的、权威的 post-action state，并比较目标不变量。

反模式：“返回没有异常，所以成功。”
正确做法：“返回任务 ID；随后读取该任务，确认负责人、截止时间和状态均与请求一致。”

5. 工具上线清单

  • 参数是否能由模型稳定生成，枚举是否闭合？
  • 错误是否结构化区分可重试与不可重试？
  • 副作用、影响范围和权限要求是否明确？
  • 是否支持幂等键或安全的状态查询？
  • 超时后能否判断动作到底有没有发生？
  • 是否定义权威核验来源和成功不变量？
  • 敏感字段是否从提示词、轨迹与错误信息中隔离？
  • 高风险动作是否具备预览、确认与补偿路径？

结论：可靠工具不是“能被调用的 API”，而是一份可被 Harness 执行、验证和恢复的协议。

Trace-native Evaluation：从一次得分到持续改进

NOTE 03 · EVALUATION & OBSERVABILITY · 13 MIN READ · 2026

Agent 的质量不是一个最终答案分数。它是一条轨迹：用了什么上下文、为何选这个工具、参数是否正确、外部状态是否完成、失败能否恢复。Trace-native Evaluation 把评测对象从“输出”扩展到“过程与结果”。

IN THIS NOTE1. 为什么单点评分失效2. 四层评测栈3. 轨迹作为一等数据4. 从线上失败生成回归集5. 发布门禁

1. 为什么单点评分失效

两个 Agent 可能给出同样的最终答案，但系统质量完全不同：一个使用了正确证据并安全完成动作；另一个依赖偶然猜测、重复执行副作用，只是碰巧得到相同结果。只看 final answer 会遗漏路径风险。

更合理的质量分解是：

Task Quality = Outcome × Process Integrity × Operational Reliability

Outcome:             用户目标是否达成
Process Integrity:   证据、选择、参数、权限是否正确
Operational:         延迟、成本、恢复、稳定性是否可接受
图 1 · 可信 Agent 位于结果、过程完整性与运行可靠性的交集。

2. 四层评测栈

  1. Deterministic checks：Schema、权限、引用、状态不变量、代码测试。便宜、稳定，适合作为第一道门。
  2. Model-based judges：用于语义正确性、任务完成度、表达质量；必须校准并监控偏差。
  3. Trace review：检查计划、工具选择、参数、恢复和人工介入是否合理。
  4. Online outcomes：用户纠正率、任务完成率、回退率、重复动作率、投诉与人工接管。

四层不是互相替代。确定性检查负责硬约束，模型评审覆盖语义空间，轨迹审查解释失败，在线指标判断真实价值。

图 2 · 越靠上越接近真实价值，越靠下越适合高频自动化。

3. 轨迹作为一等数据

一条可评测轨迹至少应包含：

  • 用户目标与归一化任务定义；
  • 上下文条目的来源、时间、检索分数与裁剪结果；
  • 模型版本、提示词版本、策略版本；
  • 每一步动作候选、最终选择与约束结果；
  • 工具参数、耗时、错误、重试和返回摘要；
  • 事后核验证据、人工介入点和最终业务状态。

同时要避免把完整敏感内容无边界写入轨迹。实践中应采用字段白名单、敏感值脱敏、内容摘要和受控采样。

4. 从线上失败生成回归集

最有价值的评测集不是一次性手工构造，而是从生产轨迹持续生长。一个闭环通常包含：

图 3 · 线上证据不是事后报表，而是下一版 Harness 的训练场。

最小化尤其重要：保留导致失败的必要上下文和工具状态，删除无关噪声，使问题可以稳定复现。每个 case 应绑定失败分类、期望不变量、允许的动作集合和成本预算。

5. 发布门禁

Agent 发布不能只比较一个总分。建议按风险维度设置门禁：

  • 关键任务成功率不得回退；
  • 高风险工具误调用必须为零或进入人工检查点；
  • 参数正确率、引用完整率达到场景阈值；
  • 重复副作用、无限循环、未核验成功为零容忍项；
  • P95 延迟与单任务成本不超过预算；
  • 新增失败模式必须有解释、回滚与监控方案。
评测的最终目标不是证明新版本更聪明，而是证明它在目标场景下更值得信任。

结论：当 Trace、Evaluation 和 Release Gate 连接起来，Agent 工程才从“调 Prompt”升级为可持续的软件交付体系。
